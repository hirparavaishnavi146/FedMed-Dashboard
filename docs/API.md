# FedMed API

FastAPI backend for the FedMed dashboard. Every response below is real output
captured from a running server, not invented.

**Read this first:** all data is synthetic. No model is trained, no federated
learning runs, no hospital is connected and no patient data is present. The API
states this in its description, in every response's `meta.notice`, and in the
`isSimulated` / `trainsModel` fields on the training endpoints.

## Conventions

**Response envelope.** Every `/api/v1` success response is `{"data": ..., "meta": ...}`.
`/health` is deliberately bare so a plain uptime probe can read it.

```json
"meta": {
  "generatedAt": "2026-10-10T09:06:06.131544Z",
  "simulated": true,
  "source": "synthetic",
  "notice": "Synthetic values generated by the FedMed backend for interface development. No model is trained, no federated learning runs, no real hospital is connected and no patient data is present."
}
```

**camelCase everywhere.** Python is snake_case internally; every response and
error body is camelCase, because that is what the TypeScript frontend reads.

**Errors** always have one shape, so the client needs one parsing path:

```json
{
  "error": {
    "code": "hospital_not_found",
    "message": "No simulated hospital with id 'HOSP-99'.",
    "detail": {
      "hospitalId": "HOSP-99",
      "available": ["HOSP-01", "HOSP-02", "HOSP-03"]
    }
  }
}
```

| Status | When | Typical `code` |
|---|---|---|
| 200 | Success | — |
| 201 | Simulated job started | — |
| 404 | Unknown id or path | `hospital_not_found`, `model_not_found`, `not_found` |
| 405 | Wrong method for a path | `method_not_allowed` |
| 409 | Conflicts with current state | `training_already_running`, `training_not_running` |
| 422 | Body or query failed validation | `validation_error` |
| 501 | Feature deliberately not built | `not_implemented` |
| 500 | Unexpected server error (details go to the log, not the response) | `internal_error` |

### `GET /api/v1/training/status`

The state of the **simulated** job. `isSimulated` is always `true` and
`trainsModel` is always `false`.

```json
{
  "data": {
    "state": "idle",
    "isSimulated": true,
    "trainsModel": false,
    "jobId": null,
    "config": null,
    "totalRounds": 0,
    "completedRounds": 0,
    "currentRound": null,
    "startedAt": null,
    "finishedAt": null,
    "secondsPerRound": 4.0,
    "message": "No simulated training job has been started. The baseline round history below is seeded sample data.",
    "history": []
  },
  "meta": { "...": "as above" }
}
```

`state` is one of `idle`, `running`, `completed`, `stopped`.

### `GET /api/v1/training/history`

| Query | Type | Notes |
|---|---|---|
| `limit` | int 1–200 | Keep at most this many rounds (newest kept) |
| `min_round` | int ≥ 1 | Only rounds at or after this number |

Returns the running job's rounds if a job has started, otherwise the seeded
baseline of 8 rounds. Each row: `round`, `status`, `globalLoss`, `globalDice`,
`globalAccuracy`, `participants`, `expectedParticipants`, `durationSeconds`,
`timestamp`.

`GET /api/v1/training/metrics` returns the same rounds shaped for the charts:
`round`, `loss`, `validationLoss`, `dice`, `accuracy`.

### `POST /api/v1/training/start`

**This starts a simulated job. It does not train a model.**

The backend advances one round per `secondsPerRound` of wall-clock time and
reports metrics from a fixed curve. Nothing is loaded, computed, aggregated or
written to disk. There is no PyTorch, MONAI or Flower code involved.

Body (optional — omit it and the defaults are used):

```json
{ "config": { "rounds": 3, "localEpochs": 2 } }
```

Returns **201** with a `TrainingStatus` where `state` is `running`.

| Config field | Default | Accepted range |
|---|---|---|
| `rounds` | 10 | 1–50 |
| `localEpochs` | 2 | 1–20 |
| `learningRate` | 0.001 | > 0 to 0.1 |
| `batchSize` | 2 | 1–8 |
| `aggregation` | `FedAvg` | `FedAvg`, `FedProx`, `FedAdam` |
| `minClients` | 2 | 1–3 |
| `validationSplit` | 0.2 | 0.05–0.5 |
| `randomSeed` | 42 | 0–99999 |
| `patchSize` | 64 | 32–128 |
| `useDifferentialPrivacy` | false | stored only; nothing is applied |

Ranges match the frontend form exactly, so both reject the same values.
`rounds × localEpochs` is capped at 200, because the reference machine is CPU only.

**409** if a job is already running (`training_already_running`).

### `POST /api/v1/training/stop`

Stops the running simulated job. Returns **200** with `state: "stopped"`.
Returns **409** (`training_not_running`) if no job is running.

Honest completion message:

> Simulated job finished all 3 rounds. Metrics are generated values, not the
> result of training.

### `GET /api/v1/model/results`

```json
{
  "data": {
    "models": [
      {
        "version": "v0.1.0", "createdAt": "2026-10-09T18:06:06.127997Z",
        "status": "archived", "dice": 0.581, "iou": 0.412, "accuracy": 0.822,
        "loss": 0.548, "sensitivity": 0.604, "specificity": 0.901, "rounds": 3,
        "notes": "First smoke-test of the aggregation loop. Single-fold validation."
      }
      // ...3 versions
    ],
    "activeVersion": { "...": "v0.2.0" },
    "bestVersion": { "...": "v0.3.0, highest Dice" },
    "latestVersion": { "...": "v0.3.0, newest" }
  },
  "meta": { "...": "as above" }
}
```

`activeVersion` and `bestVersion` are separate on purpose: the newest version is
not automatically the best. Also: `/versions`, `/versions/{version}`,
`/comparison`, `/targets` (design goals, not achievements).

Since Stage 4 the payload also carries two honesty fields and the measured
experiment, so a placeholder can never be read as a result:

```json
{
  "registryIsIllustrative": true,
  "registryNotice": "Every value in `models` is illustrative sample data. No segmentation model produced these numbers.",
  "measuredExperiment": { "available": true, "...": "see below" }
}
```

`models` holds illustrative sample values only. Measured results are **never**
merged into it — they are a separate field of a separate type, which is what stops
the two being read as one list of comparable results.

### `GET /api/v1/model/experiment`

The measured results of the standalone 3D U-Net experiment, read from the artifact
written by `python -m app.imaging.pipeline`. Reading this endpoint never starts
training.

**When a run exists:**

```json
{
  "data": {
    "available": true,
    "source": "...\\backend\\experiments\\imaging\\experiment.json",
    "site": "HOSP-01",
    "generatedAt": "2026-10-10T17:24:11Z",
    "config": { "epochs": 3, "batchSize": 1, "learningRate": 0.001, "seed": 42,
                "validationFraction": 0.34, "targetShape": [32, 32, 32] },
    "epochs": [
      { "epoch": 1, "trainLoss": 0.5615, "validationLoss": 0.4715,
        "validationDice": 0.9054, "validationIou": 0.8271,
        "validationSamples": 1, "durationSeconds": 1.9 }
      // ...
    ],
    "epochCount": 3,
    "firstTrainLoss": 0.5615, "lastTrainLoss": 0.4370, "lossImproved": true,
    "bestDice": 0.9764, "bestEpoch": 3,
    "holdout": { "dice": 0.9764, "loss": 0.4271, "cases": 1,
                 "source": "best checkpoint re-evaluated from disk" },
    "model": { "architecture": "UNet3D", "features": [8, 16, 32],
               "parameterCount": 350809, "outputIsLogits": true },
    "provenance": { "dataSource": "synthetic phantoms, procedurally generated",
                    "containsPatientData": false, "clinicallyValidated": false,
                    "isDemoValue": false, "splitBy": "case",
                    "note": "These are measurements from real local training..." }
  },
  "meta": { "...": "as above" }
}
```

**When no run exists:**

```json
{
  "data": {
    "available": false,
    "epochs": [],
    "bestDice": null,
    "lastTrainLoss": null,
    "unavailableReason": "No imaging experiment artifact found. Run `python -m app.imaging.pipeline` to produce one; until then every value shown is illustrative."
  }
}
```

`available` is explicit rather than inferred from nulls, and an unrun experiment
reports **`null`, never `0.0`**. A zero Dice renders as a measured failure, which
is a different and false statement from "nothing has run". `isDemoValue` defaults to
`true` when the artifact does not assert provenance, so an unrecognised file is not
trusted as a measurement.

The artifact location can be overridden with `FEDMED_IMAGING_EXPERIMENT`. The
default search order is `backend/experiments/imaging/experiment.json`, then
`experiments/imaging/experiment.json` (relative to the process working directory
and to the repo root).

## CORS

Allowed origins come from `FEDMED_CORS_ORIGINS`, defaulting to the Vite dev and
preview servers on both `localhost` and `127.0.0.1`. `*` is not the default, and
in production the API refuses a wildcard unless
`FEDMED_ALLOW_ALL_ORIGINS_IN_PRODUCTION` is set explicitly.

Verified: a preflight from `http://localhost:5173` returns
`access-control-allow-origin: http://localhost:5173`; a request from
`http://evil.example.com` returns no CORS header.

## Configuration

Copy `.env.example` to `.env` in `backend/` and edit it. `backend/.env` wins over
the repository-root `.env`, and both are found regardless of the working
directory. See `.env.example` in either location for every variable with comments.

## Not implemented

Being explicit, because the API is asked about these. This list is kept honest: an
entry is removed when the thing behind it is built and verified, not when it is
started.

- **Clinical validation.** Nothing here is a validated medical device. The MRI
  segmentation model is trained on synthetic volumes, and the report analysis is an
  aid for preparing a consultation, not a diagnostic.
- **At-rest encryption.** Mechanism status reports this as `not implemented`. Uploaded
  reports and staging files rely on filesystem permissions, not encryption.
- **Real patient data.** All bundled data is synthetic. Nothing checks or attests to
  the provenance of what you upload.
- **A database.** State is in memory (sessions, dataset registry, job history) or on
  disk as files (checkpoints, experiment artifacts). A restart clears the former.
- **Automatic cross-healthcare-node deployment.** The federated runs use in-process
  clients on one host; they demonstrate the aggregation and privacy mechanisms, not a
  production multi-site rollout.

Implemented, with the mechanism state reported live by `GET /api/v1/security/status`:
Flower-based federated simulation with FedAvg, PyTorch + MONAI 3D U-Net training,
secure aggregation, differential privacy accounting, API-key auth and a TLS option.

## Endpoints: datasets, cases and medical reports

These were added after the sections above and are documented here by group rather
than endpoint by endpoint, because every one of them carries a description in the
live schema:

```cmd
curl http://127.0.0.1:8000/openapi.json
```

| Group | Prefix | Notes |
| --- | --- | --- |
| Datasets | `/api/v1/datasets` | Validate, assign to a simulated hospital, prepare, train. `readyToTrain` is `validated AND assigned`. |
| Cases | `/api/v1/cases` | Mixed-file intake with a per-file classification and an honest summary. |
| Medical reports | `/api/v1/medical-reports` | Below. |

### Medical report analysis

Handles real medical documents, so **every route requires the `train` scope — reads
included.** This is deliberately stricter than the synthetic dashboard endpoints.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/medical-reports/health` | AI provider and OCR availability, limits, `authRequired`. |
| `POST` | `/api/v1/medical-reports/sessions` | Create a session (max 3 reports). |
| `GET` | `/api/v1/medical-reports/sessions/{id}` | Session state and its reports. |
| `DELETE` | `/api/v1/medical-reports/sessions/{id}` | Remove the session and delete its staged files. |
| `POST` | `/api/v1/medical-reports/upload` | `multipart/form-data`: `session_id` + 1..3 `files`. Rejections are per file. |
| `POST` | `/api/v1/medical-reports/extract` | Deterministic facts: values, printed ranges, dates, diagnoses, red flags. |
| `POST` | `/api/v1/medical-reports/confirm` | Record that the reports are for the same patient. Required before comparing. |
| `POST` | `/api/v1/medical-reports/compare` | Consistent, differing and one-report-only analytes; missing information. |
| `POST` | `/api/v1/medical-reports/analyze` | The full analysis. Returns an `analysisId`. |
| `GET` | `/api/v1/medical-reports/analysis/{id}` | Fetch a stored analysis again. |

How the result is split, and why it matters:

| Section | Computed by | When AI is unconfigured |
| --- | --- | --- |
| A. Summary of reports | Deterministic digest, plus optional AI prose | Digest shown; the AI part is absent |
| B. Findings and abnormalities | **Deterministic** — a value is only called abnormal if its own report printed a range it falls outside | Unchanged |
| C. Possible complications | AI only | `available: false` with the reason |
| D. Diagnosis status | **Deterministic** | Unchanged |
| E. Clinical suggestions | AI only | `available: false` with the reason |
| F. Urgency and safety | Deterministic red-flag scan; AI may escalate, never de-escalate | Unchanged |
| G. Doctor-ready summary | Deterministic assembly; AI prose only if configured | Assembly shown, prose absent |

Two behaviours are load-bearing and tested:

1. **Comparing before confirming the patient returns `422
   same_patient_not_confirmed`.** A comparison across different patients is
   meaningless, so it is refused rather than warned about.
2. **A red flag sets `urgency.showBeforeAnalysis = true`**, and the frontend renders
   the emergency notice above everything else. The analysis does not wait for the
   remaining reports.
